# Phase 6 작업 계획서 — 판매계획 실제 스키마 반영 + 분류 체계 정형화 로드맵

- 근거 문서: [.docs/03_데이터정제.md](../03_데이터정제.md) §6, [.docs/02_prd.md](../02_prd.md) F2·F3·데이터 모델·미해결 질문 2·17번

## 배경/동기

`판매계획_더미데이터.xlsx`를 분석한 결과, 지금까지 가정했던 "팀·년·월·계획매출액" 4컬럼 스키마는 실제와 전혀 다르고, 실제로는 거래처×제품군×월 단위로 판가·수량이 따로 들어오며 금액은 수식(판가×수량)으로 계산해야 한다는 것을 확인했다(§6.1). 또한 이 파일에는 "본부보고용(제품군 매핑)"이라는, 기존 product_group(차량AS/차량OE/산업용)·product_type(매핑표 제품구분3)과는 이름도 값도 겹치지 않는 제3의 분류 축이 있다는 것도 확인했다. 사용자는 이 세 분류 체계가 "비슷하지만 다른 데이터"라는 것을 인지하고, 당장 억지로 통합하지 말고 정형화(표준화)할 수 있는 향후 계획을 세워두길 원한다.

## 범위

**이번에 구현**: `sales_plan_record`를 실제 구조에 맞게 재설계하고, `판매계획` 파일을 실제 시트 구조(팀별 시트 4개 + `인자` 매핑 시트)대로 파싱해 F3 "계획 대비 달성률" 계산에 반영한다.

**이번에 구현하지 않음(범위 밖)**:
- `team_pl_record`(손익계산서) 실제 계정과목 파싱 — 별도 작업으로 분리(Todo 리스트에 이미 미구현으로 표시됨).
- 세 분류 체계(product_group/product_type/hq_report_group)의 실제 통합 — 아래 "분류 체계 정형화 로드맵"에 단계별 계획만 세우고, 실제 통합은 원본 데이터 확인 후 진행한다.

## 방법

1. `backend/app/db.py` — `sales_plan_record`를 PRD 데이터 모델(§6.1 갱신분)에 맞게 재설계: team, customer_code, customer_name, delivery_code, delivery_name, sales_rep, category, product_type, hq_report_group, year, month, unit_price, quantity, planned_amount. 기존 컬럼(planned_quantity, raw_payload)은 새 스키마와 이름이 달라 `COLUMN_MIGRATIONS`로 새 컬럼을 추가한다(Day 5에서 정립한 패턴).
2. `backend/app/services/plan.py` 전면 재작성 — openpyxl로 다중 시트를 직접 읽는다(팀별 시트 4개는 `pd.read_excel`의 단일 시트 가정을 벗어나므로 기존 `read_dataframe`을 쓰지 않는다):
   - `인자` 시트를 [팀, 제품군] → 본부보고용 딕셔너리로 먼저 파싱한다.
   - 팀별 시트(고정형/모티브/차량대리점/차량OE) 각각에서 헤더 행("담당" 셀 탐색)을 찾고, 데이터 행마다 담당/팀/거래처/영업담당/구분/제품군을 읽은 뒤 1~12월 각각의 판가·수량을 읽어 금액=판가×수량을 직접 계산한다(원본 셀의 캐시값은 신뢰하지 않는다 — §6.1 근거).
   - 연도는 시트 제목 셀("2026년 산전 고정형 판매계획...")에서 정규식으로 추출한다.
3. `backend/app/routers/uploads.py` — 파일 종류가 "계획"이면 새 `parse_plan_workbook`을 호출하도록 분기(다른 파일 종류는 기존 `read_dataframe` 경로 유지).
4. `backend/app/services/aggregation.py` — plan_amount 조회를 "단일 행 조회"에서 "팀·연·월로 GROUP BY SUM"으로 변경한다(세부 거래처×제품군 행이 여러 개이므로).
5. 테스트: 축소된 실제 구조를 반영한 xlsx 픽스처(팀 시트 1~2개, 거래처 2~3건, `인자` 매핑 일부)를 만들어 파서 단위 테스트와 업로드→집계 통합 테스트를 작성한다.

## 분류 체계 정형화 로드맵 (사용자 요청 — 향후 계획)

현재 확인된 세 축은 다음과 같이 서로 다른 목적의, 겹치지 않는 데이터다.

| 축 | 출처 | 예시 값 | 현재 용도 |
|---|---|---|---|
| product_group | 실적 파일 F4 요구사항(참고 양식) | 차량AS/차량OE/산업용 | F4 Overview 팀별 집계의 상위 분류 |
| product_type | 매핑표(제품분류 시트) 제품구분3 | "GB 소형" 등 | 실적 F2 정제 시 계획비교용으로 VLOOKUP하는 값 |
| hq_report_group | 판매계획 `인자` 시트 | CGS/ES/GSL/LM/MSB/PS/... | 판매계획 파일 내부에서만 쓰이는 상위 분류 |

**1단계 (이번 개발, 지금 적용)**: 세 축을 억지로 매핑하지 않고 각자 별도 필드로 저장한다. `sales_plan_record.hq_report_group`은 F3·F4 계산에 아직 쓰지 않고 원본 그대로 보존만 한다(추후 분석 대비).

**2단계 (실제 원본 파일 확보 후)**: 담당자에게 실제 SAP 실적 파일·판매계획 파일·손익계산서 파일을 동시에 받아, 같은 제품(같은 손익센터+제품코드)이 세 파일에서 각각 어떤 product_group/product_type/hq_report_group 값으로 나타나는지 실측 대조표를 만든다. 이 작업 없이는 세 축의 관계(상위-하위 관계인지, 서로 독립된 다른 분류 기준인지)를 추정으로 확정하지 않는다(CLAUDE.md "근거 없는 값 금지" 원칙).

**3단계 (관계 확정 후)**: 2단계에서 확인된 관계를 바탕으로 표준 "제품 분류 마스터" 테이블(또는 세 축 간 크로스 매핑 테이블)을 설계한다. 세 축이 완전히 독립적이라면 무리하게 하나로 합치지 않고 별도 테이블로 유지하되, 상호 조회(JOIN)가 가능하도록 공통 키(예: 제품코드)를 확정한다.

**4단계 (표준화 이후)**: F3 "계획 대비 달성률"과 F4 ⑦ "제품군별 분석"이 필요에 따라 hq_report_group 또는 표준 마스터 테이블을 활용하도록 확장한다. 이 단계는 PRD v2 로드맵(P1 매핑표 자동 학습과 인접한 항목)으로 편입할지 별도 항목으로 둘지 그때 결정한다.

이 로드맵은 `.docs/02_prd.md` 미해결 질문에도 번호를 부여해 추적한다.

## 완료 기준

- `sales_plan_record`가 실제 판매계획 파일 구조(거래처×제품군×월, 판가/수량/계산된 금액)로 저장된다.
- F3 계획 대비 달성률이 팀 단위로 합산된 실제 계획 금액을 기준으로 계산된다.
- 백엔드 pytest 전체 통과(새 파서 단위 테스트 포함).
- 분류 체계 정형화 로드맵이 PRD 미해결 질문에 단계별로 기록된다.
