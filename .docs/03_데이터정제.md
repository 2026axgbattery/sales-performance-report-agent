# 데이터 정제 — SAP 실적 원본 → 손익분석용 정제 테이블 구조 분석

- 최초 분석 대상 파일(수식 구조 분석용): `2026년 07월 3. 손익분석 (1단계 작업용)_더미더미.xlsb` — 계정과목별 산출 수식(§4)은 이 파일을 근거로 한다.
- **실제 규모·컬럼명 재검증 파일**: `2026년 08월 3. 손익분석 (1단계 작업용)__과제용.xlsb`(프로젝트 루트) — 담당자가 제공한 실제 규모의 파일로, 시트 구성·컬럼명·행 구조가 07월 참고 파일과 다른 부분이 있어 아래 내용을 갱신했다. 이 파일은 `.xlsb`라 pyxlsb로만 열 수 있는데, pyxlsb는 수식 텍스트를 읽지 못하고 계산된 값만 보여주므로 **이 파일로는 계산 값·컬럼명·행 구조만 재검증했고, 수식 로직 자체는 07월 참고 파일의 분석(§4)을 그대로 따른다.**
- **수식 원문이 살아있는 유일한 파일**: `클로드 실적 데이터 분석용_2.xlsx`(프로젝트 루트) — 담당자가 실적 Raw Data 141개 컬럼 전체 목록(8개 그룹)을 직접 정리해서 제공했고, 이 파일을 열어 실제 헤더와 1:1 대조해 전부 일치함을 확인했다(§2). 이 파일은 "손익 센터" 컬럼을 쓰는 방식(§4.1 참고)이며, **헤더가 한 행이 아니라 "엇갈린 2행" 구조다** — 1행에는 계정과목명(매출액(Total) 등)이 식별자 컬럼(상품/고객/손익 센터 등) 자리만 비운 채 들어있고, 2행에는 그 식별자명이 채워져 있는 대신 계정과목 컬럼 자리엔 "1 KRW"/"1 AH" 같은 단위 라벨이 들어있다(§2 참고, F1 업로드 파이프라인이 실제로 이 구조의 파일로 크래시를 겪어서 `app/services/validation.py`의 `read_dataframe`이 컬럼별로 두 행 중 값이 있는 쪽을 골라 병합하도록 구현되어 있다). **지금까지 분석한 다른 실적 파일은 전부 `.xlsb`(pyxlsb는 계산된 값만 읽고 수식 텍스트를 못 읽음)였는데, 이 파일은 `.xlsx`라 `openpyxl(data_only=False)`로 Re-arrange 시트의 실제 수식 원문(77개 컬럼 전체)을 그대로 읽을 수 있었다** — 그동안 6029행 값 대조로 역산 검증했던 §4.4·§4.5 공식들과 대조해 대부분 일치를 재확인했지만, 두 가지 실제 오류를 발견해 정정했다: (1) 판관인건비는 대손상각비를 포함한 9개가 아니라 **8개 항목**이 맞고 대손상각비는 "기타-판관비" 잔여값 쪽에 흡수된다(§4.5 정정 참고), (2) "수량(22.9cell)" 조건이 대소문자를 가리지 않고(`V전지:SET`) "V전지:set/oe"라는 두 번째 트리거 값도 있다(§4.7 정정 참고) — 값 대조만으로는 두 값이 우연히 같아서 발견하지 못했던 오류다.
- 목적: 실제 담당자가 SAP에서 받은 원본 실적 데이터를 엑셀 수식으로 어떻게 "정제 자료"로 가공하는지 그 구조를 파악해, PRD([.docs/02_prd.md](02_prd.md)) F2(데이터 정제 및 매핑)의 실제 구현 로직 근거로 삼는다.
- **시트는 4개다**(07월 참고 파일 분석 당시엔 3개로 파악했으나, 08월 파일로 재확인한 결과 `지점코드`가 하나 더 있다): **실적 Raw Data**(원본), **실적 Re-arrange용 수식**(정제 결과), **지점코드**(팀+거래처코드 → 권역·사업소·파트 매핑표), **제품분류**(팀+제품코드 → 제품구분 매핑표).
- **F1·F2 업로드 경계(담당자 확인)**: F1의 "실적 파일"은 **[실적 Raw Data] 시트의 내용·형식만** 업로드한다. **[지점코드]와 [제품분류]는 향후 하나의 "맵핑표" 파일로 함께 업로드**할 예정이다 — `app/services/mapping.py`의 `parse_mapping_upload`가 xlsx/xlsb 매핑표 파일에서 "제품분류"·"지점코드" 두 시트를 각각 찾아 파싱하도록 구현되어 있다(§3.5, §6.3 참고. CSV는 지점코드 없이 제품분류만 담당). 실적 분석 시 앱이 자동으로 이 맵핑표를 참조해 [실적 Re-arrange용 수식] 시트의 정제 로직을 적용하고, 이후 판매계획·손익계산서와의 비교 작업까지 이어간다.

## 2. 실적 Raw Data 시트 — 원본 필드 구조

**근거 파일**: `클로드 실적 데이터 분석용_2.xlsx`(프로젝트 루트) — "실적 Raw Data"(141개 컬럼) · "실적 Re-arrange용 수식"(77개 컬럼) 두 시트를 담고 있는 담당자 제공 파일. 헤더는 1행이 아니라 **2행**에 있다(1행은 일부 계정과목 컬럼에만 있는 그룹/단위 라벨이고, 3행부터 실데이터). 담당자가 사전에 141개 컬럼 전체 목록을 정리해준 것을 이 파일과 대조해 전부 일치함을 확인했다.

## 4. 실적 Re-arrange용 수식 시트 — 정제 로직 (컬럼별 수식 매핑)

Re-arrange 시트의 각 행은 Raw Data의 같은 행 번호를 참조한다(4행 ↔ 4행, 1:1 매핑이며 별도 필터링·정렬 없이 좌우 재배열만 수행). 수식은 아래 6가지 패턴으로 분류된다.

**① 원본 컬럼 직접 복사/이름 변경** — 예: `L(영업-정마감매출) = Raw!H`, `M(영업-기타매출액) = Raw!I`
**② 식별자 파싱** — 코드+설명이 합쳐진 원본 텍스트를 `LEFT`/`MID`/`RIGHT`/`TRIM`/`SUBSTITUTE`로 분리
**③ 코드 → 명칭 매핑 (IF)** — 손익센터 숫자 코드를 팀 이름으로 치환
**④ 제품코드 → 제품구분 매핑 (VLOOKUP)** — 제품분류 시트 조회
**⑤ 항목 합산/차감** — 여러 원본 컬럼을 더하거나 다른 정제 컬럼끼리 차감해 소계·조정값 산출
**⑥ 최종 손익 계산** — 매출·원가·판관비 최종 확정값으로 영업이익 산출

### 4.1 식별자 컬럼 (A~H)

| 컬럼 | 헤더 | 정제 로직 | 패턴 |
|---|---|---|---|
| A | 년 | `=RIGHT(Raw!D, 4) & "년"` — 기간/연도 문자열 끝 4자리 | ② |
| B | 월 | `=TRIM(MID(Raw!D, 9, 4))` — 9번째 위치부터 4자 추출 | ② |
| C | 팀 | `=IF(Raw!C=20342,"모티브", IF(Raw!C=20345,"고정형", IF(Raw!C=20313,"차량대리점","차량OE")))` — 손익센터 코드 매핑, 나머지는 전부 "차량OE"로 처리 | ③ |

> **실제 운영 파일과의 차이(2026-08 Raw Data로 확인)**: 이 표는 07월 참고 파일 기준으로 "손익센터"가 순수 정수 컬럼이라고 분석한 것이었다. 실제 운영 파일에서는 (1) 헤더 텍스트가 "손익센터"가 아니라 "손익 센터"(공백 포함)이고, (2) 값 자체가 "고객"·"상품" 필드와 같은 "코드+설명" 합성 형식(앞 5자리 숫자가 손익센터 코드)이라는 것을 사용자가 확인해줬다. `app/services/identifiers.py`의 `parse_profit_center`가 이 형식을 파싱한다(§4.1 하단 참고).

- **검증 방법**: 08월 실제 파일 전체 6029행에서 BO열(매출수량)과 BZ열(수량(22.9cell))을 행 단위로 비교했다(pyxlsb는 계산된 값만 읽을 수 있어 수식 텍스트는 확인 불가 — §4 서두 참고).
- **확인된 규칙**: 전체 6029행 중 **팀="모티브" AND 제품구분1(보고4용)="V전지:Set"인 546행만** `수량(22.9cell) = 매출수량 × 22.9`이고, **그 외 전 행(5483행)은 `수량(22.9cell) = 매출수량`으로 환산이 없다(비율 1)**. 546행 전부가 정확히 22.9(부동소수점 오차 범위 내)였고, 다른 배율은 발견되지 않았다.
- **22.9라는 값의 출처 확인 시도**: 이 546행에 해당하는 Raw Data의 용량(단위당)/총용량/연량(단위당)/총연량 컬럼 값을 확인했으나(예: PIJ00484T → 용량(단위당)=250, 연량(단위당)=66026.767 — 전압·용량값으로 22.9와 무관), 어떤 컬럼에도 22.9라는 값이 없었다. 즉 특정 제품 속성에서 유도되는 값이 아니라, **"V전지:Set"(모티브팀 지게차용 배터리 SET 품목) 제품군 전체에 적용되는 고정 환산 계수(22.9)**로 판단된다 — 이 계수의 업무적 의미(예: SET당 표준 셀 환산 개수)는 담당자에게 별도 확인이 필요하다.
- **구현**: `app/services/identifiers.py`의 `apply_cell_22_9_conversion(product_group_1, quantity)`이 이 규칙을 그대로 반영한다(제품구분1(보고4용)이 "V전지:Set"이면 ×22.9, 아니면 그대로). `refine_row`는 R/QZZ 예외 규칙(BO, §4.6)을 적용한 값을 `quantity_raw`에 보존하고, 여기에 이 환산을 추가로 적용한 값을 `quantity`(BZ 상당)로 저장한다. F3(이상징후 판단의 평균단가 등)·F4(Overview 집계)는 모두 `refined_sales_record.quantity` 컬럼을 그대로 합산/평균하므로, 컬럼명을 바꾸지 않고도 "수량(22.9cell)"이 기본 수량으로 자동 반영된다.
- **정정(수식 원문 확보 후)**: `클로드 실적 데이터 분석용_2.xlsx`로 실제 수식 텍스트를 확인한 결과 `=IF(OR(N="V전지:SET", N="V전지:set/oe"), BW*22.9, BW)`다. 값 기반 검증(6029행)만으로는 못 잡았던 두 가지 차이가 있었다: (1) 엑셀의 문자열 비교는 기본적으로 대소문자를 가리지 않는데 파이썬은 가린다 — `apply_cell_22_9_conversion`을 대소문자 무시 비교로 고쳤다. (2) "V전지:Set" 외에 **"V전지:set/oe"**라는 두 번째 트리거 값이 있다 — 이전엔 한 파일에서만 검증해서 놓쳤다. 지금은 두 값 모두(대소문자 무시) 인식한다.

## 5. PRD 대비 확인된 사실 및 반영 필요 사항

이번 원본 파일 분석으로 [.docs/02_prd.md](02_prd.md) "10. 미해결 질문"의 1번 항목(계정과목3 산출 수식)과 2번 항목(실제 컬럼 스키마)에 대한 실제 근거가 확보되었다. PRD가 가정했던 로직과 실제 로직 사이에 다음과 같은 차이가 있어, PRD를 갱신할 때 반영이 필요하다.

1. **"계정과목1+계정과목2=계정과목3" 가정은 실제와 다르다.** 실제로는 항목마다 로직이 다르다 — 단순 복사(①), 합산(⑤), 뺄셈(⑤), 역산(⑤, 예: 기타매출원가·기타판관비처럼 상위 소계에서 하위 항목을 뺀 잔여값), 코드 매핑(③④), 최종 손익 계산(⑥)이 항목별로 섞여 있다. F2 요구사항 문서를 "계정과목별 개별 산출 규칙 68종"으로 재정의해야 한다.
2. **제품 매핑은 "제품코드"만이 아니라 "팀 구분 + 제품코드" 합성 키로 조회한다.** 매핑표(제품분류 시트)의 스키마도 단순 2컬럼(코드-제품군)이 아니라 인자/팀/제품/구분/용도/제품구분1~4/자재내역의 10개 컬럼 구조이며, 이 중 상황에 맞는 제품구분 컬럼(현재는 3번, 계획비교용)을 선택해서 쓴다.
3. ~~**원본 데이터에 "안내/가이드 행"이 섞여 있다.**~~ — **해결됨(08월 실제 파일로 재확인).** 07월 참고 파일에만 있던 안내 행이었고, 실제 업무 파일(08월)에는 1~3행 안내 행이 없다 — 헤더가 1행, 데이터가 2행부터 바로 시작한다(§1 참고). F1의 `read_dataframe`이 이미 기본값(첫 행=헤더)으로 읽고 있어 별도 스킵 로직이 필요 없다.
4. **Standard(S) vs Actual(A) 이중 원가 체계가 존재한다.** 원본에는 모든 원가 항목이 표준원가(S)와 실제원가(A) 두 버전으로 내려오지만, 정제 테이블은 Actual(A) 계열만 채택한다. F2 요구사항에 "어떤 원가 기준을 사용하는지"를 명시해야 한다.
5. **팀 구분 코드 매핑에 불일치가 존재한다** (§4.1 주의 사항 참고) — 모티브/고정형 팀이 매핑 조회 시 동일한 "산전" 키를 사용하는 부분은 실제 업무 담당자에게 의도된 설계인지 확인이 필요하다.
6. **수량 계산에 예외 규칙이 있다** — 제품코드가 `R` 또는 `QZZ`로 시작하면 매출수량을 0으로 처리한다. 이런 코드 접두사 기반 예외 규칙이 이 외에도 있는지 확인이 필요하다.
7. **컬럼 헤더 텍스트에 오탈자(닫는 괄호 누락)가 다수 있다(08월 실제 파일로 확인).** "원재료비_칼슘연(A"·"주재료비_격리판(A"뿐 아니라 "기타수익(Total"·"기타비용(Total"·"금융수익(Total"·"금융비용(Total"·"연구개발비(국책과제"·"수출비용_해상운임("·"투자자산처분및손상차"처럼 열려있는 괄호가 닫히지 않은 헤더가 더 있다(§2 참고). `REQUIRED_RAW_COLUMNS`는 실제로 쓰는 컬럼만 실측해 반영했지만, F2 구현 범위를 넓힐 때 새로 참조하는 컬럼은 항상 실제 파일 헤더 텍스트를 먼저 확인해야 한다 — 이름으로 추정하지 않는다.
8. ~~지점코드 매핑표가 별도로 존재하며 아직 구현되지 않았다~~ — **해결됨.** Re-arrange 시트의 부문·권역·사업소·파트는 "팀+거래처코드" 합성 키로 지점코드 시트를 조회한 결과이며(§3.5), `app/services/branch.py`로 구현하고 08월 실제 파일 50행으로 실제 값 일치까지 검증했다. 다만 Re-arrange 시트의 "부문" 컬럼은 아직 구현하지 않았다 — 부문(예: "차량", "산전")이 팀에서 바로 유도되는지 별도 매핑이 필요한지 확인이 안 됐다.
9. ~~담당자가 BZ열(수량(22.9cell))을 추가하고 이를 기본 수량으로 확정했다~~ — **해결됨.** §4.7에서 규칙(모티브팀+V전지:Set만 ×22.9, 그 외 1:1)을 08월 실제 파일 전체 행으로 검증했고, `app/services/identifiers.py`의 `apply_cell_22_9_conversion`으로 구현해 `refined_sales_record.quantity`가 이 값을 갖도록 반영했다(예외 규칙 적용 전 값은 `quantity_raw`로 별도 보존). 22.9 계수 자체의 업무적 의미(왜 정확히 22.9인지)는 여전히 미확인이다.

이 발견 사항들은 PRD F2 상세 요구사항과 데이터 모델(계정과목 관련 필드)을 업데이트할 때 근거 자료로 사용한다.

## 6. 판매계획·팀별 손익계산서 파일 구조 (더미 샘플 분석)

사용자가 제공한 `판매계획_더미데이터.xlsx`, `손익계산서_더미데이터.xlsx`(둘 다 프로젝트 루트에 저장됨, 더미 데이터라는 안내 문구가 파일 내부에 명시되어 있음 — 담당/거래처명/코드/수량/금액은 전부 무작위 값)를 분석해, PRD 미해결 질문 2번("판매계획·팀별손익계산서 파일의 실제 컬럼 스키마 없음")의 근거를 확보했다. `app/services/plan.py`(팀·년·월·계획매출액 4컬럼 가정)와 `team_pl_record`(원본을 파싱하지 않고 raw_payload로만 보관)는 아래 실제 구조와 크게 다르므로, F2·데이터 모델을 이 구조에 맞춰 재검토해야 한다.

### 6.1 판매계획_더미데이터.xlsx

- **시트 구성**: `제품군별 SUMMARY`(집계, 수식 미계산이라 전부 공백) / `고정형`·`모티브`·`차량대리점`·`차량OE`(팀별 상세, 실제 값 있음) / `인자`(제품군 매핑표).
- **팀은 4개**(고정형/모티브/차량대리점/차량OE)만 등장하고 **"산전팀"은 나타나지 않는다** — 03_데이터정제.md §4.1에서 확인한 실적 데이터의 팀 매핑 수식(4개 분기, 산전팀 분기 없음)과 일치한다. PRD 미해결 질문 13번("산전팀 실존 여부")에 참고가 되는 정황 증거이나, 이 파일이 더미이므로 이 자체로 13번을 확정하지는 않는다.
- **팀별 상세 시트 컬럼**(1행: 안내문구, 15~16행: 2단 헤더, 17행부터 데이터): 담당, 팀, 유통채널, 고객(코드), 고객명, 납품처(코드), 납품처명, 영업담당, 구분(예: "상품"/"광주"/"창원" — 정확한 의미 미확인, 생산거점 또는 유통 구분으로 추정되나 근거 없음), **제품군**(예: LM, CGS 소형, V-Type(Cell), AGM 3세대 등 — 세부 품목 단위. 기존 앱의 "제품구분"(매핑표 제품구분3, 예: "GB 소형")에 대응하는 개념으로 보이나 값 자체는 겹치지 않음), 제품코드(더미 데이터에서는 항상 공백), **기준기간(25년 8월 누계) 판가/수량/금액**, **1~12월 각각 판가/수량/금액**(월 36컬럼), 연평균판가/연간수량합계/연간금액합계/판가차이/차이율/비고, **본부보고용(제품군 매핑)**.
- **"금액" 컬럼은 저장된 값이 아니라 `=판가×수량` 수식이며, 이 더미 파일은 Excel에서 한 번도 계산되지 않아 캐시값이 없다** — `pd.read_excel`(openpyxl 캐시값 읽기)로는 전부 `NaN`으로 보인다. 실제 파일을 파싱할 때는 캐시값을 신뢰하지 말고 **판가×수량을 직접 계산**해야 한다(SAP/경영기획 산출물에서 흔한 패턴이므로 실제 원본 파일도 동일할 가능성이 높다 — 확인 필요).
- **"본부보고용(제품군 매핑)" 컬럼도 수식**: `=VLOOKUP("고정형"&J18,인자!A:D,4,0)` — "팀+제품군 합성 키"로 `인자` 시트를 조회하는 구조로, 기존 실적 매핑표의 "팀 구분+제품코드 합성 키" 패턴과 동일한 접근 방식이다. `인자` 시트는 [팀, 제품군, 본부보고용] 3컬럼이며, 팀별로 서로 다른 제품군 목록을 갖고 본부보고용(예: CGS/ES/GSL/LM/MSB/PS/RP/VGS/리튬-기타/산업용/V-Type(Cell)/Longest(EB) 등)으로 묶는다. **이 "본부보고용" 값은 기존 데이터 모델의 product_group(차량AS/차량OE/산업용)이나 product_type(매핑표 제품구분3)과도 이름이 겹치지 않는, 판매계획 전용의 제3의 분류 축으로 보인다** — 실적·계획·손익계산서 세 파일의 제품 분류 체계를 어떻게 통합할지 원본 데이터로 재확인이 필요하다.
- **가격변동율의 실제 근거를 확인**: 판가차이(`연평균판가-기준판가`)·차이율(`판가차이/기준판가`) 컬럼이 F4 데이터 모델의 `price_change_rate` 개념과 정확히 대응된다.
- 고객/납품처 코드+명칭 구조는 F4 ⑧ "팀별×거래처별 상세"·`CustomerResult` 모델의 customer 필드 근거가 될 수 있다.

### 6.2 손익계산서_더미데이터.xlsx

- **시트 구성**: `국내`(전사 집계, 수식 미계산이라 전부 공백) / `모티브`·`고정형`·`대리점`·`차량oe`(팀별 상세, 실제 값 있음).
- **팀별 상세 시트 구조**: 행 = 계정과목(구분), 열 = 1~12월 + 1~4분기 + 상반기/하반기 + 총계, 단위는 "대, 백만원". 계정과목 행 목록이 03_데이터정제.md §4에서 확인한 실적 Re-arrange 시트의 68개 계정과목과 상당 부분 일치한다(매출수량, 매출액(Total), 매출원가(A)Tot, 상품매출원가, 재고실사차이, 환불부채, 평가손실, 관세환급, 매출원가조정기타, 원재료비_순연/경연/칼슘연, 원재료(LOSS_*), 원재료비_니켈(A)/리튬(A), 주재료비_전조/카바/격리판(A), 부재료비(A), 포장비(A), 부대품재료비(A), 부산물공제(A), 변동직접노무비(A), 변동경비(A), 고정직접노무비(A), 간접노무비(A), 고정경비(A), 외주가공비(A), 원가절감(구매/광주/창원/품질/국내/해외), 매출총이익(A), 판관비(Total), 임원급여, 직원급여, 임원상여, 직원상여, 임금, 제수당, 잡급, 퇴직급여, 대손상각비, 복리후생비, 여비교통비 등).
- **`국내` 시트(전사 집계)는 팀별 시트를 합산하는 수식으로 보이나, 마찬가지로 캐시값이 없어 전부 공백으로 읽힌다** — 파싱 시 팀별 시트에서 직접 합산해야 한다.
- 이 구조는 PRD의 `TeamPLRecord`(record_id, file_id, batch_id, team, account_item, amount, period)에 대응시킬 수 있으나, 현재 백엔드는 이 파일을 파싱하지 않고 raw_payload로만 저장하고 있다 — 실제 계정과목별 파싱 로직 구현이 필요하다.

> **금액 단위 불일치 발견 및 확정(Phase 12)**: 이 가로형 파일(과 이름이 비슷한 `2026년 경영계획 수정_팀별_공장별 손익계산서_더미용.xlsx`)은 표에 적힌 대로 **"백만원" 단위**로 값이 들어있다. 반면 §6.2.1의 세로형 파일과 실적(Re-arrange) 쪽 금액은 전부 **"원" 단위**다. 이 둘을 그대로 섞어서 `team_pl_record`에 저장하면 계획 대비 비교 시 100만 배 스케일 차이가 난다 — 실제로 Phase 12 검증 중 이 문제를 겪었다. **사용자 확인 결과 "원 단위가 맞다"** — 즉 이 가로형 더미 파일의 금액 값(백만원 단위)은 실제 업로드 형식을 대표하지 않으며, 앞으로 손익계산서 업로드는 §6.2.1의 세로형(원 단위)을 기준으로 삼는다. 가로형 파서(`TEAM_SHEET_TO_TEAM` 기반)는 코드에는 남아있지만, 실제 운영 데이터로는 이 단위 불일치 때문에 신뢰하지 않는다 — 실사용 중 이 형식의 실제 파일이 나오면 단위를 먼저 실측 확인해야 한다.

### 6.2.1 손익계산서_더미용.xlsx — 실제 업로드 형식(세로형, 신규 확인)

담당자가 F1로 실제 업로드할 형식을 별도 파일(`손익계산서_더미용.xlsx`, 프로젝트 루트)로 제공했는데, §6.2의 가로형(팀별 시트)과 **완전히 다른 구조**다.

- **시트 1개**("손익계산서 자료")뿐이고, **세로형(long format)**이다 — 행 = 팀×월 조합(모티브 1~12월 → 고정형 1~12월 → 차량대리점 1~12월 → 차량OE 1~12월, 총 48행 + 여분 공백행), 열 = 계정과목 81개(1열=팀, 2열=월, 3열부터 매출수량~이익률).
- 팀명이 이미 앱 표준 명칭 그대로다(`차량OE`, `대리점`이나 `차량oe`가 아님) — §6.2에서 겪었던 "시트명↔표준 팀명 불일치" 문제가 이 형식에는 없다.
- 81개 계정과목 컬럼 순서가 Phase 11에서 분석한 다른 참고 파일의 "계획" 시트(§4.5 근거 파일 중 하나, `2026년 08월 4. 손익분석 (2단계 배포용) 1.xlsb`)와 정확히 일치한다 — `app/services/pl_comparison.py`의 `PLAN_ITEM_GROUPS`가 이미 이 이름들을 그대로 기대하도록 짜여 있어 그대로 맞는다.
- **파일 어디에도 연도 정보가 없다**(시트 제목도 없고 별도 연도 컬럼도 없음) — 사용자 확인 결과, **같은 배치로 업로드되는 실적 파일의 연도(target_year)를 그대로 쓰기로 확정**했다.
- **구현 완료** — `app/services/team_pl.py`의 `parse_team_pl_workbook`이 이제 두 형식을 자동 판별한다(팀별 시트가 있으면 가로형, 1행이 `["팀","월",...]`로 시작하는 시트가 있으면 세로형). `app/routers/uploads.py`는 실적 파일로 `target_year`를 확정한 **뒤에** 손익계산서 파일을 파싱하도록 순서를 바꿔서 이 연도를 세로형 파서에 전달한다. 실제 파일로 종단 업로드까지 확인했다(팀 4개×월 12개×계정과목 79개 = 각 팀 948행, 연도가 실적 파일의 target_year(2026)와 정확히 일치).

### 6.3 반영 필요 사항 요약

1. PRD `SalesPlanRecord`, `TeamPLRecord` 데이터 모델을 위 실제 구조에 맞게 재정의해야 한다(미해결 질문 2번 갱신 대상).
2. `backend/app/services/plan.py`의 "팀·년·월·계획매출액" 4컬럼 가정은 실제 구조(거래처×제품군×월, 판가/수량 별도)와 다르므로 재구현이 필요하다.
3. F3 "계획 대비 달성률"은 현재 `aggregated_result`(팀×product_group, product_group=차량AS/차량OE/산업용) 단위로 계산되는데, 판매계획 데이터는 거래처×제품군(세부 품목) 단위로 들어오므로 팀 단위로 먼저 집계(SUM)한 뒤 비교해야 한다 — 세부 제품군 단위 계획 대비는 이번 파일의 "본부보고용" 매핑 체계를 추가로 반영해야 가능하다.
4. `team_pl_record`도 실제 계정과목 파싱 로직 구현이 필요하다(현재는 raw_payload 보관만 함).
5. 위 파일들은 "더미데이터"로 명시되어 있어 실제 SAP/경영기획 산출물과 세부 값은 다를 수 있다 — 스키마(시트 구성·컬럼 구조·수식 패턴)는 신뢰할 수 있는 근거로 삼되, 팀 목록·제품군 명칭 등 구체적 값은 실제 원본 확인 전까지 잠정으로 취급한다.
